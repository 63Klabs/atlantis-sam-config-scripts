# create_repo.py: reject zip members that extract outside the temp directory

> **Status**: Locked, 2026-11-14
> **Issue**: [ISSUE.md](ISSUE.md) (GitHub issue #12)
> **Reviewed against**: `main` at `74f0688` on 2026-11-14 (clean `cli/` tree). The issue was written against `480e089`; the extraction loop has since moved from `cli/create_repo.py:566-580` to `:679-711`.

## 1. Summary

`RepositoryCreator._download_and_extract_into` builds each output path as `Path(temp_dir) / <zip member name>` and writes to it without checking that the result stays inside `temp_dir`. A member named `../x` or `/abs/x` writes outside the temporary directory. The write first deletes any existing file at that path, so it can replace a file the user can write. Directory members are created outside the directory too.

The zip comes from `--source` or the organization's starter list, so this is hardening of a low-risk path, as the issue says. It matters when someone points `--source` at a zip they do not control. This plan confirms the issue by running the existing code against a scratch directory (Section 2).

The recommended fix adds one private containment check that runs on the final `output_path` for every member (file or directory, both source types), raises a dedicated error before anything is written for that member, and goes through the existing failure path (CodeCommit repository deleted, GitHub cleanup prompt or `--cleanup-on-failure`). The issue's "without creating the repository" is read as "without seeding": the repository is created before the zip is downloaded, and this spec keeps that order (Decision 2). The first unsafe member fails the whole run (Decision 1).

## 3. Current state

- **Flow** (`cli/create_repo.py:263-300`): `_create_repository()`, then `_create_dev_test_branches()`, then `_download_and_extract()`, then `_seed_repository()`. All of it runs inside one `try` that, on GitHub, calls `_handle_github_seeding_failure()` and then `_cleanup_github_clone()` before re-raising.
- **Temp directory ownership** (`:595-617`): `_download_and_extract` creates `temp_dir` with `tempfile.mkdtemp()`, removes it on any failure, and hands it to the caller on success. The downloaded zip is stored inside it as `source.zip` (`:620`).
- **Extraction** (`:659-731`): for GitHub sources, finds a single top-level directory shared by all non-directory members and strips it. Then for each member computes `output_path`, creates parents, reads the member as bytes, unlinks any existing file, and calls `write_bytes`. Members are never turned into symlinks, so no link-based escape exists.
- **Failure handling** (`:724-731`): logs, deletes the CodeCommit repository (CodeCommit only), and calls `sys.exit(1)`. On GitHub the cleanup is offered once by `create_and_seed_repository`.
- **Member names on Windows**: `zipfile.ZipInfo.__init__` normalizes `os.sep` to `/` (checked in the Python 3.12 stdlib source), so `..\x` on Windows becomes `../x`. On Linux a backslash stays a literal filename character, which is harmless there. On Windows `Path` also treats `C:/x`, `D:x`, and `\\host\share\x` on the right side as non-relative (checked with `PureWindowsPath`), so a containment check on the resolved path handles those too.
- **History**: the loop is from the original script (`951e5566` and `2ca37a61` in `git blame`). The last edits are the byte-write change from the `binary-and-non-utf-8` spec and the cleanup work from `issue-creating-github-repository-error-getting`. Both are committed in `74f0688`. There is no earlier path-safety decision to preserve.
- **Existing safe pattern in the repo**: `cli/update.py:389-395` checks `dest.startswith(os.path.abspath(target_dir))` and raises `ValueError`. It has a weakness (Section 5) and is a different script with a different trust profile, so it is not reused.
- **Tests that encode current behavior**: none touch traversal. `tests/test_create_repo_tempdir_cleanup.py` builds small zips (`:76`) and exercises `_download_and_extract` failure paths, and `tests/test_create_repo_download_failure_cleanup.py` covers the GitHub cleanup handler. Both give fixtures to reuse. Baseline: `pytest tests/test_create_repo_*.py` passes, 137 tests.
- **Sibling specs in 0.0.21** touching the same loop: `binary-and-non-utf-8-files-are-seeded-as-base64` (locked, implemented) and `issue-creating-github-repository-error-getting` (locked, implemented). No conflict remains.

## 4. Review

### 4.1 Security

- **Trust boundary.** The zip bytes and every member name are attacker-controlled when `--source` is not trusted. The script is run by a user with credentials, so the reachable damage is whatever that user can write on the workstation or CI runner. Typical targets are files in the user's home or the working tree.
- **Fail closed.** The check must raise before any path is created or written for that member. Skipping is the fail-open option and is not offered (Decision 1).
- **Output injection.** The member name is untrusted. It is printed to the terminal and logged. Print it with `repr()` (or equivalent escaping) so control characters and ANSI escape sequences in a name cannot rewrite the terminal or forge log lines. Truncate very long names.
- **Check on the final path.** The check runs on the path actually written, after prefix stripping, so a name that is safe before stripping and unsafe after is caught. `Path.resolve()` is applied to the target and the parent. The extraction directory is created by this process and holds no symlinks (nothing creates them), so resolving is reliable.
- **Windows-only name tricks** (alternate data streams `name:stream`, reserved device names such as `CON`, trailing dots and spaces) do not escape the directory and are not addressed by containment. They are left as a note (Section 7).
- **Resource use.** No limit on member count, member size, or total size. Whole members are read into memory (`:704`). This is a denial-of-service concern on the user's own machine, not an escape. Confirmed spin-off (Decision 4).
- **IAM.** No change. No new AWS or GitHub calls.
- **Disclosure.** The issue is already public as GitHub issue #12, is described there as hardening with no known incident, and the repository is public. Keep exploit detail in this plan to the harmless names above. No private handling is needed. The changelog entry should say "reject zip members that resolve outside the extraction directory" without a how-to.

### 4.2 Software engineering

- **One helper, one call site.** Add a private static method (for example `_resolve_member_path(base_dir, relative_name)`) in `create_repo.py` that returns the checked path or raises `UnsafeZipMemberError` (a `ValueError` subclass defined in the same file, PascalCase with `Error` suffix per `naming-conventions-python`). Call it at the single place `output_path` is used, so the three assignment sites stay as they are. Python 3.14 is the documented target (`docs/00-Set-Up-Local-Environment.md:16`), so `Path.is_relative_to` is available.
- **Validate before writing.** The simplest form that avoids a half-extracted directory is a first pass that computes and checks every `(member, output_path)` pair, then a second pass that writes. Because the run fails as a whole (Decision 1), the temp directory is deleted on failure anyway, so a half-written temp directory is not harmful. Validation inside the existing loop is enough and no first pass is needed.
- **Error path.** `UnsafeZipMemberError` is caught in the existing `except Exception` block (`:724`). Add a specific `except UnsafeZipMemberError` in front that prints a clear message (member name escaped, plus "the source zip is unsafe or corrupt, nothing was seeded"), then runs the same steps as the generic handler (`_delete_codecommit_repository()` for CodeCommit, `sys.exit(1)`). The exit code stays 1 and the temp directory is still removed by `_download_and_extract`.
- **Documentation.** Update the `create_repo.py` section of `docs/SCRIPT-GUIDE.md` (`:13`) with a sentence on rejection. It says the run exits 1, that a CodeCommit repository is deleted, and that a GitHub repository is kept unless the prompt is answered `y` or `--cleanup-on-failure` is set (Decision 2). Add Google-style docstrings with Example to the new helper and exception (`documentation-standards-python`).
- **Versioning.** `cli/create_repo.py` is `v0.2.5/2026-11-14` and today is 2026-11-14, so under `ascs-cli-script-versioning` the version stays unchanged if the work lands today, otherwise PATCH. Decide at implementation time by comparing dates.
- **Changelog.** Entry under `v0.0.21 (unreleased)`, category **Security**, in the style of the neighbouring entries, with the spec link and `addresses #12`. State that a rejected zip exits with status 1 and that the repository is created before the zip is checked, so on GitHub the existing cleanup prompt or `--cleanup-on-failure` applies. Repositories seeded earlier are unaffected (a traversing member never reached a repository).
- **Tests.** Follow `test_create_repo_*.py`: build zips in the test, call `_download_and_extract_into` with mocked downloads (the pattern in `tests/test_create_repo_tempdir_cleanup.py`), and assert on the filesystem. The repo already uses `hypothesis`.

### 4.3 Cloud engineering

- No infrastructure, IAM, or template change.
- **CodeCommit path**: the repository is created, then deleted by the existing failure path (`_delete_codecommit_repository`, attempted once, prints the manual command if deletion fails). A `codecommit:CreateRepository` and `DeleteRepository` pair is spent per rejected zip. That is the existing cost model for any extraction failure.
- **GitHub path**: the repository is created, then the user is prompted (default `N`) or `--cleanup-on-failure` deletes it. In CI without that flag a rejected zip leaves an empty private repository behind. This is the existing behavior for every seed failure (locked in the `issue-creating-github-repository-error-getting` spec, Decision 3).
- **Rollout.** `cli/` ships through `update.py`, so the fix reaches users on their next update. No stage or alarm concerns.

## 5. Gaps and observations

- **Reorder point (Decision 2).** The issue's "without creating the repository" cannot be met by the check alone. Kept as is. The reorder is a confirmed spin-off (Decision 5).
- **`source.zip` name collision** (not in the issue). The downloaded zip lives inside the extraction directory as `source.zip` (`:620`). A member named `source.zip` at the top level overwrites it while it is open. On Linux the extraction continues from the unlinked file and then `os.remove(zip_path)` (`:713`) silently deletes the member's file, so it is dropped from the seed. On Windows the unlink of the open file fails and extraction aborts with the generic error. Stays inside the directory, so not a traversal. Note only.
- **`update.py` check weakness** (`cli/update.py:393`). `dest.startswith(os.path.abspath(target_dir))` has no separator, so a member that resolves to a sibling such as `cli-evil/x` passes for target `cli`. The per-file `except Exception` also logs and continues instead of aborting. Different script, different source (release zip from GitHub or the organization), and `update.py` replaces itself, so changes need care. Spin-off (Decision 3).
- **Symlink members** (mode bits in the zip) are written as regular files containing the link target text, so they cannot be used for escapes. Pin with one test.
- **Duplicate member names** and case-colliding names on case-insensitive filesystems: last write wins today. Not a safety issue. Not addressed.
- **Docs that exist**: `docs/SCRIPT-GUIDE.md` `create_repo.py` section. No doc currently claims extraction safety.
- **Tests affected**: none must change. New tests only.

## 6. Proposed approach

### 6.1 Change

1. Add `UnsafeZipMemberError(ValueError)` and a private static `_resolve_member_path(base_dir, relative_name)` to `cli/create_repo.py`. The helper computes `base = Path(base_dir).resolve()` and `target = (base / relative_name).resolve()`, and raises when `target` is not `base` or inside it (`Path.is_relative_to`). It is called with the same `relative_name` the loop already uses (`rel_path` after prefix stripping, otherwise `zip_info.filename`). Both source types use the one call, and directory members are checked before `mkdir`.
2. In `_download_and_extract_into`, catch `UnsafeZipMemberError` ahead of the generic handler and print a specific message with the escaped member name. Behavior otherwise matches the generic handler (CodeCommit repository deleted, exit 1, temp directory removed by the caller, GitHub cleanup prompt from the outer handler). The first unsafe member fails the whole run (Decision 1). The repository-creation order is unchanged (Decision 2).
3. Containment is the only rule. A name such as `a/../b.txt`, which stays inside, is accepted (Decided D1).
4. Tests, new file `tests/test_create_repo_zip_safety.py`:
   - S3 branch and GitHub branch (with and without the stripped prefix), for `..` file members, absolute file members, directory members, and a member that is unsafe only after prefix stripping.
   - A scratch sentinel file outside the extraction directory is unchanged and no new file appears outside after rejection.
   - Exit code 1, CodeCommit repository deleted once, GitHub failure handler runs once, temp directory removed.
   - Error output contains the escaped name and no raw control characters.
   - Benign zips (nested dirs, `a/../b.txt` staying inside, all-`../` GitHub prefix, symlink-mode member) extract as before.
   - A `hypothesis` property: for generated member names, every extracted file ends up under the extraction directory or the run is rejected.
5. Docs and changelog as in 4.2.

### 6.2 Alternatives considered

| Alternative | Why not |
|-------------|---------|
| `ZipFile.extractall()` / `ZipFile.extract()` | They sanitize names silently (drop `..` and leading slashes) rather than reject, and they would change the byte-write and prefix-stripping behavior locked by earlier specs. |
| Reject any name containing a `..` segment or a drive/absolute prefix lexically | Stricter, but needs Windows-specific cases, and rejects harmless names that stay inside. The resolved-path check covers the same attacks. |
| Reuse the `update.py` check | It has the prefix-sibling weakness (Section 5). |
| Skip bad members and continue | Silently seeds a partial, possibly broken starter into a new repository (Decision 1). |
| Download and validate before creating the repository | Literal reading of the issue, but rewires failure ownership in `create_and_seed_repository` (Decision 2, Decision 5). |

### 6.3 Decided in this plan (veto-able)

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Containment of the resolved path is the only rule. Names that stay inside are accepted. | Matches the issue's expected behavior. Fewer false rejections of unusual but valid archives. |
| D2 | The helper lives in `create_repo.py`, not `cli/lib/`. | One caller. A `lib/` change would ship to `update.py` users along with scripts that do not use it, and `update.py` replaces itself. |
| D3 | The error shows the member name with `repr()` escaping and a length cap, and logs the same. | Names are attacker-controlled (Section 4.1). |
| D4 | Directory members are checked as well as file members. | `mkdir(parents=True)` on an unchecked path creates directories outside (claim 4). |
| D5 | Windows-only name tricks (ADS, reserved names) are not handled. | They do not escape the directory. Noted in Section 7. |
| D6 | No change to the CLI surface. No new flag. | Hardening only. Version stays PATCH or unchanged. |
| D7 | The three confirmed spin-offs were filed on 2026-11-15 with the `enhancement` label only: [#15](https://github.com/63Klabs/atlantis-sam-config-scripts/issues/15) (`update.py` containment check, Decision 3), [#16](https://github.com/63Klabs/atlantis-sam-config-scripts/issues/16) (member count and size limits, Decision 4), [#17](https://github.com/63Klabs/atlantis-sam-config-scripts/issues/17) (validate the zip before creating the repository, Decision 5). | Keeps this spec to the containment fix. Each issue describes the finding as low risk and gives no exploit detail. |

## 8. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| False rejection of a legitimate starter | The four public Atlantis starters are checked in a test run against their downloaded zips (anonymous HTTPS, see `atlantis-TEST::list_starters`) before release. Zips from `zip` and GitHub never contain `..` or absolute names. |
