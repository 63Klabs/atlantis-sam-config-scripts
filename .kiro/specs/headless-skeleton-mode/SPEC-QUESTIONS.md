# Clarifying Questions for Headless & Skeleton Mode

After reviewing `cli/config.py` and its supporting libraries, I have the following questions before proceeding with the spec-driven development process.

---

## Skeleton Mode Questions

### Q1: Skeleton File Naming Convention
The skeleton JSON file stored in `local-init/` — should it follow the same naming pattern as the samconfig files? For example:
- `local-init/{prefix}-{project_id}-{infra_type}.json`
- `local-init/{prefix}/{project_id}/{infra_type}.json` (nested directories)
- Something else?

**Answer:**

Use `local-init/{prefix}-{project_id}-{infra_type}.json` 
After a successful headless configuration the file should be deleted. it is temporary.

### Q2: Skeleton File Structure
You mentioned the format should be "similar to the CloudFormation create-stack CLI JSON." The AWS CLI `create-stack` accepts a JSON like:
```json
{
  "StackName": "...",
  "TemplateURL": "...",
  "Parameters": [
    { "ParameterKey": "Key1", "ParameterValue": "Value1" }
  ],
  "Tags": [
    { "Key": "TagKey", "Value": "TagValue" }
  ]
}
```

Should the skeleton use this exact AWS format, or should it mirror the internal config structure that `build_config()` produces (which has `atlantis.deploy.parameters`, `deployments.{stage}.deploy.parameters.parameter_overrides`, etc.)? The internal structure carries more context (s3_bucket, region, confirm_changeset, role_arn) that the AWS format doesn't natively include.

**Answer:**

mirror the internal config structure that `build_config()` produces

### Q3: Template Selection in Skeleton Mode
In skeleton mode, you said the user will still be prompted for the template. After template selection:
- Should the skeleton include the full template S3 URI (with versionId) or just the template filename?
- Should the skeleton include metadata about the template parameters (descriptions, allowed values, constraints) as comments/hints to help the user fill it out?

**Answer:**

- just the template filename
- Also include a property "applyTemplateUpdateIfAvailable" with default as "y" to answer the question if there is a template update available.
- Yes, the skeleton include metadata about the template parameters (descriptions, allowed values, constraints) as comments/hints to help the user fill it out

### Q4: Pre-populating Skeleton Values
You mentioned the skeleton should "take in the values of any current sam config file for that deployment, defaults, etc." If an existing samconfig exists:
- Should those values be pre-filled in the skeleton as the default values?
- If no samconfig exists, should it fall back to the defaults hierarchy (defaults.json → prefix-defaults.json → prefix-project-defaults.json → infra_type/defaults.json, etc.)?
- Should stage-calculated defaults (DeployEnvironment, RepositoryBranch based on stage_id) also be pre-populated?

**Answer:**

Yes, the values should be pre-filled. If no sam config exists, it should fall back to the same process config.py uses.

### Q5: Skeleton Tags Section
Tags in the current flow come from multiple sources: automated tags (generated from parameters), default tags (from settings/defaults), CodeCommit repo tags, and user-entered custom tags. For the skeleton:
- Should automated tags (Atlantis, atlantis:Prefix, Provisioner, etc.) be excluded since they're generated at deploy time?
- Should only user-editable tags (from `tag_keys` in settings + defaults + custom) be included in the skeleton?

**Answer:**

- Exclude the automated tags since they are generated by config.py
- only include user-editable tags

### Q6: Multiple Stages in Skeleton
The current config supports multiple deployment stages (test, beta, prod) in a single samconfig. Should the skeleton:
- Only represent a single stage (the one specified by the positional `stage_id` argument)?
- Support multiple stages in one skeleton file?

**Answer:**

- Only represent a single stage (the one specified by the positional `stage_id` argument)

## Headless Mode Questions

### Q7: Headless Validation
In headless mode, should the script:
- Validate all parameter values against the template constraints (AllowedPattern, AllowedValues, MinLength, etc.) and fail with an error if invalid?
- Or should it accept values as-is and let CloudFormation reject them at deploy time?

**Answer:**

It should validate. However, we don't want to duplicate effort, so ensure we use the skeleton file as input instead of user prompts and and perform validation. If an error, we should fail with a reason.

### Q8: Headless Git Operations
The interactive flow includes `Git.prompt_git_pull()` at the start and `Git.prompt_git_commit_and_push()` at the end. In headless mode:
- Should git operations be skipped entirely?
- Should they be performed automatically without prompting?
- Should there be flags to control this (e.g., `--no-git`, `--auto-git`)?

**Answer:**

Perform them automatically without prompting. Do not add the additional git flags


### Q9: Headless Deploy Prompt
At the end of the interactive flow, the user is asked "Do you want to run the deploy script now?" In headless mode:
- Should deploy be skipped by default?
- Should there be a `--deploy` flag to trigger it?
- Or should the skeleton file include a field indicating whether to auto-deploy?

**Answer:**

Include the --deploy flag to trigger. 
We should also add a headless mode --headless to the deploy.py which is called for deploying. It should auto perform the git functions and override the confirm changeset. It should NOT use the skeleton file. The skeleton file is only for config.py, deploy.py will use the samconfig file.


### Q10: Headless Error Handling
If the skeleton/init JSON file is missing required fields or has invalid values, should headless mode:
- Fail immediately with a clear error message listing all issues?
- Fail on the first issue encountered?
- Fall back to interactive mode for missing/invalid fields?

**Answer:**

Fail immediately with a clear error message listing all issues

### Q11: Headless Stack Check
The `--check-stack` flag compares local config against the deployed stack and prompts the user to choose. In headless mode:
- Should `--check-stack` be incompatible with `--headless`?
- Or should it default to using the local config (skeleton values) without prompting?

**Answer:**

`--check-stack` should be incompatible with `--headless`

## General Questions

### Q12: Mutual Exclusivity
Should `--headless` and `--skeleton` be mutually exclusive flags, or could they theoretically be combined (e.g., generate skeleton then immediately run headless)?

**Answer:**

They should be mutually exclusive.

### Q13: Existing Config Handling in Skeleton Mode
If a samconfig already exists for the given prefix/project/infra_type/stage, and the user runs `--skeleton`:
- Should it overwrite the existing skeleton file?
- Should it merge/update the skeleton with current values?
- Should it prompt (since skeleton mode is interactive for template selection)?

**Answer:**

It should overwrite any existing skeleton file. The samconfig file is the source of truth. The skeleton file is temporary.

### Q14: local-init Directory Location
Should `local-init/` be at the project root (same level as `cli/`, `defaults/`, `local-templates/`) or somewhere else? Should it be git-ignored by default (since it may contain environment-specific values)?

**Answer:**

It should be at the project root, and it's contents should be git-ignored. Similar to local-templates. It is treated as temporary scratch area.

### Q15: Headless Mode and Defaults File Updates
At the end of the interactive flow, `check_for_default_json()` prompts the user to save certain values as future defaults. In headless mode:
- Should this step be skipped entirely?
- Should there be a field in the skeleton to indicate "save these as defaults"?

**Answer:**

Assume Yes for saving as future defaults.
